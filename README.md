# Акции по эквайрингу и СБП

Дашборд по действующим предложениям шести банков (Сбер, Альфа, ГПБ, ВТБ,
Т-Банк, БСПБ). Данные обновляет GitHub Actions по расписанию; то же самое
запускается с ноутбука одной командой.

```bash
./update.sh
```

Собрать → извлечь → проверить → пересобрать HTML → запушить. Страница
обновляется через 1–2 минуты после пуша.

## Как это устроено

```
fetch.py  →  extract.py  →  validate.py  →  build.py  →  git push  →  Pages
Playwright    Gemini         приёмка        Jinja2
```

| Файл | Что делает |
|---|---|
| `update.sh` | Прогоняет весь цикл и публикует |
| `src/fetch.py` | Открывает 6 страниц в headless-браузере, кладёт текст в `data/snapshots/<дата>/` |
| `src/extract.py` | Отдаёт текст Gemini со строгой JSON-схемой, получает структурированные условия |
| `src/validate.py` | Отбраковывает мусор и накладывает проверенное на `data/banks.json` |
| `src/build.py` | Собирает `docs/index.html` из данных и шаблона |
| `src/schema.py` | Модель данных — общая для всех четырёх шагов |
| `src/selection.py` | Решает, какие банки идут в прогон: все или только отставшие |

`data/banks.json` — единственный источник правды. HTML руками не правится:
любая правка содержания идёт в JSON, дальше `build.py`.

**Почему браузер, а не `requests`.** Пять сайтов из шести отдают обычный
SSR-HTML, но у Альфа-Банка стоит JS-челлендж ServicePipe — без браузера
приходит полтора килобайта со спиннером.

**Почему LLM, а не CSS-селекторы.** Банки перекраивают лендинги несколько
раз в год. Селектор ломается молча: отдаёт пустоту или чужое число. Модель
со схемой переживает редизайн, а от её фантазий защищает `validate.py`.

## Установка (один раз)

```bash
pip install -r requirements.txt
python -m playwright install chromium
cp .env.example .env          # и вписать ключ из https://aistudio.google.com/apikey
```

`.env` в `.gitignore` — ключ остаётся на ноутбуке и на GitHub не уезжает.

## Режимы запуска

```bash
./update.sh              # полный цикл с публикацией
./update.sh --repair     # только банки, которые отстали от остальных
./update.sh --bank vtb   # только названные банки (можно через запятую)
./update.sh --local      # всё собрать, но не пушить — посмотреть перед публикацией
./update.sh --rebuild    # только пересобрать HTML из данных: без сети, без ключа
```

`--rebuild` нужен после правки шаблона или текста в `data/banks.json`:
ходить на сайты банков ради этого незачем.

Отдельные шаги, если нужно разобраться:

```bash
python src/selection.py --report                 # у кого какие данные и что отстало
python src/fetch.py --bank alfa                  # один банк
python src/extract.py --dry-run                  # извлечь и показать, ничего не записывая
python src/validate.py --check-only              # отчёт приёмки, banks.json не трогать
python src/extract.py --snapshots data/snapshots/2026-07-21   # прогнать по старому снимку
```

Ключи выбора банков (`--bank`, `--banks`, `--stale`) понимают все три шага
одинаково — правило одно и живёт в `src/selection.py`.

## Сертификаты Минцифры

Сбер, Альфа, ВТБ и БСПБ отдают раннеру GitHub TLS-цепочку, замкнутую на
корень **Russian Trusted Root CA** УЦ Минцифры. В macOS он установлен в
системном хранилище, поэтому с ноутбука сбор проходит; на Ubuntu-раннере
его нет, и все четыре банка падали там с `ERR_CERT_AUTHORITY_INVALID`
(браузер) и `self-signed certificate in certificate chain` (запасной
путь). С 03.08 по 17.08.2026 из 51 попытки не прошла ни одна: Сбер, ВТБ и
БСПБ две недели держали данные от 3 августа, и сайт этого никак не
показывал — прогоны при этом были зелёные.

Корень и два промежуточных лежат в
[`certs/russian_trusted_ca.pem`](certs/russian_trusted_ca.pem) — это
публичные сертификаты: корень и промежуточный 2022 года скачаны с
`https://gu-st.ru/content/Other/doc/russiantrustedca.pem` и сверены с
системным хранилищем ноутбука, промежуточный 2024 года взят из живой
цепочки ВТБ и проверен подписью того же корня. Они **добавляются** к
системным корням, а не подменяют их: проверка сертификата остаётся
включённой везде, ГПБ и Т-Банк со своими обычными CA проверяются как
раньше. Chromium системным хранилищем OpenSSL не пользуется, поэтому ему
те же сертификаты передаются списком SPKI-отпечатков
(`--ignore-certificate-errors-spki-list` в `fetch.py`): ошибка цепочки
снимается только для сертификатов с этими открытыми ключами.

Отпечатков нужно три, а не один корневой: сервер присылает корень не
всегда. Сбер присылает — и прошёл сразу, ВТБ шлёт только лист и
промежуточный. Промежуточные носят одно имя `Russian Trusted Sub CA`, но
ключи у выпусков 2022 и 2024 годов разные, и банки сегодня стоят на
выпуске 2024 — по нему первый прогон и промахнулся.

Проверить, какой сертификат отдают банку сейчас:

```bash
echo | openssl s_client -connect www.sberbank.ru:443 \
  -servername www.sberbank.ru -CAfile certs/russian_trusted_ca.pem 2>/dev/null \
  | grep -E "issuer=|Verify return code"
```

С ноутбука ответ может отличаться от раннера: тем же банкам с российских
и европейских адресов прилетает обычный публичный сертификат, а с
адресов дата-центров — цепочка Минцифры. Поэтому починку этого места
видно только в прогоне на GitHub, локально она не воспроизводится.

## Если банк не обновился

Обычная причина — не приёмка и не модель, а сам сайт банка: защита от
ботов рвёт соединение с чужим дата-центром. В логе прогона это видно как
`net::ERR_CONNECTION_CLOSED` или таймаут на `page.goto`. Так 27.07.2026
из прогона выпали ВТБ и Т-Банк: страницы не отдались раннеру GitHub,
оба банка сохранили данные от 23-го и статус `stale`.

Что происходит дальше само:

- банк без свежего снимка **не затирает прошлые данные** — на карточке
  появляется «⚠️ данные от такого-то числа»;
- каждые четыре часа Actions запускает **дообновление**: берёт только
  отставшие банки и пробует ещё раз. Попытка идёт с другого адреса, и
  обычно этого достаточно;
- остальные пять банков дообновление не трогает вовсе — их данные
  переносятся в новый файл как есть, вместе со статусом и датой;
- если данные не изменились, коммита не будет: в истории сайта не
  копятся пустые правки.

Руками, если ждать не хочется:

```bash
./update.sh --repair          # с ноутбука: только отставшие
```

или на GitHub: **Actions → Обновление данных → Run workflow**, режим
`repair` либо явный список в поле `banks` (`vtb,tbank`).

Банк, который не даётся дольше недели, роняет ближайший полный прогон
(`selection.py --check-age 7`) — GitHub присылает письмо о падении. Без
этого застрявший банк неделями оставался бы незамеченным: прогон-то
зелёный, остальные обновились.

## Лимиты Gemini

Бесплатный тир даёт **20 запросов в сутки** на модель (`gemini-3.5-flash`).
Один прогон — ровно 6 запросов, по одному на банк, так что суточного лимита
хватает на три полных обновления.

Дообновление квоту почти не тратит: запрос уходит только за банк, чей
снимок удалось собрать. Самый частый случай — страницу вообще не отдали,
и такой прогон стоит ноль запросов.

Выжечь его легко, если запускать `src/extract.py` подряд при отладке: каждый
повтор считается отдельным запросом. Признак — ошибка `RESOURCE_EXHAUSTED`
с `quotaId: GenerateRequestsPerDayPerProjectPerModel-FreeTier`. Сброс в
полночь по тихоокеанскому времени, около 10–11 утра по Москве.

Проверить остаток и работоспособность ключа одним запросом:

```bash
curl -s "https://generativelanguage.googleapis.com/v1beta/models?key=$GEMINI_API_KEY" | head -5
```

На запрос стоит таймаут 90 секунд. По умолчанию его нет вовсе, и запрос,
потерявший соединение на полпути, ждёт ответа бесконечно: 30.07.2026
извлечение так простояло полтора часа на первом банке и не дошло ни до
приёмки, ни до сборки.

Модели заданы списком в [`src/extract.py`](src/extract.py): основная
`gemini-3.5-flash`, за ней `gemini-3.6-flash`, дальше две lite-модели на
случай ответа 503 «high demand». Lite заметно слабее — теряет часть
акций, — поэтому после прогона на ней стоит сверить результат глазами; в
логе видна строка «(через модель …)».
Версии зафиксированы намеренно: `gemini-flash-latest` молча переезжает
на новое поколение, и извлечение менялось бы без единой правки в коде.
По этой же причине алиас убран из списка запасных: он указывает на самое
свежее поколение, то есть на ту же перегруженную модель, что и первая
строка, и отдавал 503 ровно вместе с ней.

## Что защищает от мусора

Публикация идёт без ревью, поэтому между галлюцинацией модели и живой
страницей стоит `validate.py`:

- ставка вне 0–5%, дата дальше двух лет, акция без названия — значение выбрасывается;
- цитата, которой нет в снимке страницы, — признак выдумки, значение выбрасывается;
- пустая базовая ставка при известной прошлой — промах извлечения, а не отмена
  ставки банком: остаётся прошлая;
- акция, пропавшая из извлечения, **возвращается**, если её дословная цитата
  всё ещё есть в сегодняшнем снимке. Слабая запасная модель приносит по
  странице одну акцию вместо четырёх — 30.07.2026 у Сбера так пропадали
  компенсация НДС и два региональных предложения. Акцию, которую банк
  действительно снял, цитата не спасёт: её в снимке уже нет;
- банк без единого пригодного значения сохраняет прошлые данные и получает
  статус `stale` — на карточке появляется «данные от такого-то числа»;
- **если в полном прогоне развалилось больше двух банков, чьи страницы
  дошли до модели, `update.sh` останавливается и ничего не публикует.**

Порог считает только банки со снимком: пустой результат по прочитанной
странице означает сломанный пайплайн, и публиковать такое нельзя. Банк,
чью страницу не отдали, порогу не подсуден — 30.07.2026 именно на этом
прогон и встал: три сайта не ответили раннеру, приёмка сочла прогон
развалившимся и отменила публикацию целиком, хотя по трём остальным
данные были свежие. Теперь такие банки просто уходят в `stale` и
достаются дообновлению.

Точечный прогон порогом не связан вовсе: он и запускается потому, что
банк не даётся, а данные по остальным в файле уже верны.

Сырые снимки страниц лежат в `data/snapshots/<дата>/` (в репозиторий не
коммитятся) — по ним видно, что реально было на странице банка.

## Публикация на GitHub

Pages настроен на ветку: **Settings → Pages → Source: Deploy from a branch →
Branch: `main`, папка `/docs`** — пуш `docs/index.html` сам обновляет сайт.

Обновление данных идёт из [`.github/workflows/update.yml`](.github/workflows/update.yml):

| Когда | Что делает |
|---|---|
| Пн и чт, 11:00 МСК | Полный прогон по всем шести банкам |
| Каждые 4 часа | Дообновление: только отставшие; если таких нет — выходит за секунды, не ставя зависимостей |
| Вручную | **Run workflow**: режим `full`/`repair` или список банков в поле `banks` |

Боту нужны право `contents: write` (стоит в самом workflow) и секрет
репозитория `GEMINI_API_KEY` — тот же ключ, что в локальном `.env`.

## Добавить седьмой банк

Одна запись в `data/banks.json` — достаточно `id`, `name`, `color`,
`source_url`, `checked_at`, `status: "seed"`; остальное заполнит первый же
прогон. Ни шаблон, ни скрипты трогать не нужно.

## Оговорка

Данные собираются автоматически с публичных страниц банков и могут содержать
неточности. Страница не является публичной офертой; условия уточняйте в банке.
